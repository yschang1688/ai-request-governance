# AI Gateway PoC 報告：認證、授權與去識別化

**日期**：2026-10-19 · **預先登記**：`openspec/ai-gateway/requirements.md`（門檻 G1–G11 在寫程式前 commit，實作中未修改）
**環境**：M1 16GB 本機；Keycloak 26.4.0（OrbStack 容器，代替 Entra ID）；Gateway 與內部 API 為 FastAPI；模型為地端 Ollama qwen3.5:9b。資料全為合成。

## 一句話結論

**示意架構圖的每一層，在本機都實測擋得住它聲稱要擋的事**：G1–G10 全部達成，每一條的反向檢核（關掉對應檢查重跑）都轉紅。端到端接上地端 9B 時，測出一個回聲模型測不到的問題（模型改寫代碼括號導致沒還原），已修正並補測試。

## 實作中的發現

1. **模型會改寫代碼格式（G11 第 1 次）**：9B 把 `⟨PII_2⟩` 寫成 `⟪PII_2⟫`，Gateway 只認原格式，使用者收到代碼而非原值；稽核的未知代碼計數用同一格式比對，也沒抓到。方向是安全的（沒有洩漏），但體驗壞了、監控有盲點。**修正**：還原時容許常見括號變形，對不上的類代碼字串計入稽核；新增 G5b。第 1 次的實際失敗回答用新版重放，正確還原。第 2 次 9B 剛好沒有改寫括號，所以真模型上的證據是重放，不是第 2 次本身。
2. **姓名照樣送進模型**：「王先生」沒有被遮，符合預先列出的邊界，這次在真模型上實際看到。
3. **還原只換字、不懂語意**：第 2 次 9B 回答「所有敏感資料皆以去識別化代碼形式保存」，還原後代碼變回原值，這句話就不再正確。
4. **Keycloak 設定的坑**（細節見 design.md 的 T1、T2、T7 紀錄）：代換時要同時帶 `scope` 才能指定目標 audience；自訂 client scope 後，內建的 `sub`、角色、帳號頁所需的 mapper 都要自己補，否則 token 缺欄位、帳號頁打不開。
5. **測試本身的錯**：G8 第一次失敗是測試 helper 送出的 header 名稱帶底線，伺服器只認連字號；修的是測試，Gateway 未動。

## 邊界（這份 PoC 不能拿來宣稱的事）

- **不是 Entra ID**：Keycloak 證明的是「設計擋得住」，不是「在貴公司的 Entra 上跑過」。Entra 的 On-Behalf-Of 是微軟流程，本 PoC 用同一套標準（RFC 8693）驗證設計。條件式存取未涵蓋。
- **MFA 只手動示範一次**，不在自動化門檻內；自動化測試用密碼直取 token（Direct Grant）只為測試方便，正式環境應用授權碼＋PKCE。
- **去識別化只認格式**：身分證、手機（含 +886、全形、國字數字）、email、統編（要有標籤）、市話。認不得自由文字裡的姓名、沒有標籤的 8 位數統編。
- **使用者端提示（架構圖 ①）未實作**。
- **G1「iss 不符」不夠單純**：用另一個 realm 簽的 token，iss 與簽章金鑰同時不符，無法單獨隔離 iss 檢查。
- **G10 第三項的反向檢核形式不同**：「不帶使用者 token 不能代換」是 Keycloak 端行為，Gateway 旗標關不掉；改用對照組（同一請求補上使用者 token 即成功）證明失敗確實來自缺 token。
- **u-mfa 設定後的煙霧檢查**：只給密碼時的錯誤訊息與密碼錯相同，煙霧測試無法單獨區分，以管理端查核為準。
- 未涵蓋：效能、高可用、金鑰輪換演練、正式 SIEM 串接、Gateway 本身的 TLS（本機 http）。

```
cd ai-gateway

../.venv-gateway/bin/python -I realm/check_realm.py   # realm 煙霧測試 30 項
../.venv-gateway/bin/python run_gates.py   # G1–G10＋G5b 與反向檢核，約 20 秒
../.venv-gateway/bin/python e2e.py         # G11，需 Ollama qwen3.5:9b
```
