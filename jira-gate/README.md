# Jira AI 需求閘門：設計與驗收

把「AI 需求從收件、驗證到交付」的治理規則寫進 Jira 的工作流程，而不是寫在文件裡等人遵守。在 Jira Cloud（team-managed 專案）上實際建置，**只用內建功能，沒有外掛、沒有程式**。本目錄只放設計說明；Jira 站台是作者的個人示範站，不隨 repo 公開。

## 一句話

缺資料送不出，沒驗過交不出，退回必留痕。

## 工作流程：七站、三條退回線

```
需求收件 → 分級審查 → 已排入 → MVP 開發 → MVP 驗證 → 交付／UAT → 上線監控 → 結案
              │                     ▲          │  │
              │ 審查退回            └─驗證未過─┘  │ 驗證後放棄
              └──────────────→ 不做／退回 ←────────┘
```

9 個狀態＝7 站＋結案＋不做／退回。

## 每道出口的欄位檢查

換狀態的當下由 Jira 檢查欄位，不填就換不過去。

| 出口 | 必填 | 欄數 |
|---|---|---|
| 送審（收件 → 分級審查） | 一句話痛點、資料在哪 | 2 |
| 核准排入 | 風險等級（紅黃綠）、AI 可行性、驗收標準 | 3 |
| 審查退回 | 退回原因、退回後處置 | 2 |
| 驗證後放棄 | 退回原因、退回後處置 | 2 |
| 驗證未過，退回開發 | 退回原因、退回後處置、已試過什麼、部分結果 | 4 |
| 驗證任務：判定通過 | 結果、主指標、門檻 | 3 |
| 驗證任務：判定未過 | 結果 | 1 |

- 17 個欄位（需求單 13、驗證任務 4），其中 12 個是某道門的必填；退回原因這類欄位在多道門重複要求。
- AI 可行性的第一個選項是「規則就能做」：不是每件事都該上 AI。
- 驗收標準在分級審查就定好，驗證時只回答過了沒，不在驗證時改門檻。
- 退回開發最重：退回代表有人做了工、結果沒過，不留下試過什麼、跑到哪，接手的人只能從頭再來。

## 子任務閘門：沒驗過就交不出

驗證是獨立的子任務（待驗 → 驗證中 → 判定），不是父需求上的一個勾選框。父需求的「驗證通過，交付」轉換掛上「子任務全部須為驗證通過」：**子任務沒全過時，交付選項直接不出現**，選單裡只剩退回開發與放棄。

## 驗收：先弄壞，再相信

一個從來不會響的警報，和一個壞掉的警報，畫面上看起來一樣。所以每條規則都故意觸發過：

| 演練 | 結果 |
|---|---|
| 子任務還在驗證中，讀父需求可用的轉換 | API 只回退回、放棄兩條，交付不在其中 |
| 判定未過、不填結果 | 400＋自訂白話訊息 |
| 退回開發，依序缺 3 欄、缺 1 欄、欄位齊 | 擋、擋、放行 |
| 介面上清空「退回後處置」再按退回開發 | 跳出「轉換失敗」與自訂訊息 |

另外實驗了工單連結：設「B blocks A」、B 停在審查，A 照樣往下走兩步。**Jira 的連結只標示關係，不會擋轉換**，所以閘門用子任務限制，不用連結。

## 五張報表

各站停留天數、驗證結果分布、退回原因分布、各單位需求數、同一需求退回次數（以「處於狀態的平均次數」代替需求變更次數）。

## 設計取捨

| 不用 | 改用 | 理由 |
|---|---|---|
| 工單連結擋交付 | 子任務閘門 | 連結擋不住換狀態 |
| 自動化規則擋關卡 | 內建欄位檢查 | 擋關卡要確定；盤查、彙整、提醒這類量大重複的工作才交給自動化 |
| 第三方 AI 判工單 | 地端模型判燈號 | 判斷機不機敏本身要讀內容，工單不能為了分類先送出去；見 [`../ticket-sensitivity/`](../ticket-sensitivity/) |

判準：能用確定的規則擋，就不用會猜的元件。

## 邊界

- team-managed 專案沒有單張工單的權限隔離（issue security），要做到「A 單位看不到 B 單位的需求」需改用 company-managed 專案。
- 「誰改過工作流規則」要看管理端的 audit log，個人示範站看不到完整版。
- 必填只檢查有沒有填，不檢查填得對不對（填「無」也會過），要靠報表定期抽查。
